## Qué existe (endpoints)
- `POST /api/fm/fixtures|snapshot|run` — catálogo/snapshots. Snapshot = dual scope por fixture: 3 navs (overview + player/team trends, `location=all`) + fetch API directo 0 navs para `<tab>+loc=match`. `/run` topN = Max/3 = 13/run.
- `POST /api/fm/outcomes/resolve {date?, fixtureIds?}` — 0 navs, idempotente; UNAVAILABLE reintentable.
- `GET /api/fm/fixtures/{id}/confluence` — solo lectura, 0 navs (P3).
- `GET /api/fm/fixtures/{id}/odds` — P5 A5: devuelve `bookmakerName` resuelto vía `fm_bookmakers`.
- `POST /api/fm/fixtures/{id}/manual-odds {bookmaker,market,line,odds_value}` — C4 P4 (source=manual).
- **P6 G2 / PBI 2.1 C / P9** `POST /api/fm/teams/{teamApid}/collect {locations?|venue?=["home","away"], period?=15, stat?="corners"|stats?=["tackles","fouls-committed"]}` — contrato vigente: `stats` es una lista (o `stat` con comas) de tokens que `FmPlayerStatMap.ResolveSlug` traduce a slug FM (`tackles`, `fouls-involvements`, `fouls-committed`, `fouls-won`, `saves` + P9 `shots_created→shots-created`, `penalties→penalties`; `chances_created` queda pass-through porque FM no tiene slug para ese mercado), `venue=home,away` es alias de `locations`, y `group` se **deriva** del slug vía `FmPlayerStatMap.GroupForStat` (tackles/saves→defense, fouls-*→discipline, resto→attack) porque el pivot de `teams/table` se clavea por group, no por stat. `FmTeamController`: `teams/table` vía `FetchJsonAsync` con navigation gate (0 navegaciones, nunca solapa una nav), parsea, upsertea y guarda raw en `AppContext.BaseDirectory\tmp\fm\teams\<apId>\`. Pausa 2-4s entre fetches. Ver `docs/adr/ADR-002-player-missing-mapping.md`.
- **P10 (ítem 5 P2) `POST /api/fm/collect`** — body `{teams: long[] (obligatorio), stats?=["corners"], locations?|venue? (default home+away), period?=15, includePositions?=false}`. Orquestador global: ejecuta el **mismo** `CollectTeamBatchAsync` del collect por equipo (una sola implementación, extraída, sin código copiado) equipo por equipo, en el mismo navigation gate y con el throttle de 2-4 s que ya vive en ese loop — **el orquestador no añade paralelismo** (`FmGlobalCollectOrchestrator`, en Infrastructure para poder testearlo sin web host). Respuesta: por equipo el mismo shape que `/teams/{id}/collect` (`teamApid, period, stat, stats, locations, results[]` con `status/group/written/inserted/playerRows/warnings` por stat×location) más `error` (solo si el equipo lanzó) y `positions` (solo con `includePositions=true`, **siempre después** del teams/table de ese mismo equipo porque position-stats necesita `fm_team_matches`/`fm_player_matches`; exige `period ∈ {5,10,15,20}` — whitelist P8 J3). Resumen: `summary {teams, fetches, positionFetches, errors, elapsedMs}` con `fetches = |teams| × |stats| × |locations|`. **Errores**: 400 solo por body inválido (`teams` vacío, `locations` fuera de home|away, `period ≤ 0`, `includePositions` con period fuera de la whitelist); un fallo de fetch/parse queda como `status=NO_DATA|PARSE_ERROR` en el `results` de ese equipo (o `error` de nivel equipo si lanza excepción) **sin abortar a los demás**, y el endpoint responde 200. Diferencia deliberada con el collect por equipo: éste normaliza `period ≤ 0` a 15 (comportamiento heredado, sin cambio) en vez de rechazar. Log: `P10 global collect team {Team}: {Fetches} fetches, {Errors} errors` + las líneas G2 por stat×location.
